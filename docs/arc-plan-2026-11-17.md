# What to build next on Arc cards: Xe2, Alchemist and Xe3 (plan, 2026-11-17)

A map of what has to be made or changed in this engine, card family by card family, after reading how urakozz's B70
engine reached its MoE numbers. Nothing here is built yet. Every gain is an estimate until a card measures it.

## The memory rule (the user, 2026-11-18)

Every item here keeps its VRAM and RAM cost minimal. Concretely:
- No item may take VRAM that the context or the expert cache would otherwise get, unless it is opt-in or sized from
  the room left free at load (as `--ctx auto` and the expert cache are sized now), and the load log names what it took.
- No item adds a second copy of the weights in RAM. A CPU path reads the experts where they already are.
- New buffers are scratch, sized by the chunk or the window, and shared with existing scratch where their lives do not
  overlap.
- Each change's before-after row states its VRAM and RAM change from the load log (`GPU buffers`, the expert cache line,
  the host memory figure), beside the speed.

What each item costs, by design:

| Item | VRAM | RAM |
|---|---|---|
| X1 (experts on XMX from their raw rows) | **less**: the per-chunk int8 expert buffer (`moe_wq_` / `moe_wh_`, one group of decoded experts) goes away | none |
| X2 (chunk size) | the chunk's activations scale with it: only where the free room allows, as the chunk is chosen now | none |
| X3, X4 (fused norms, DeltaNet front) | none, or less (one intermediate buffer fewer) | none |
| X5 (`ARC_MOE_GEMM_PAD`) | the decoded gate / up of one expert group at the padded width: within the existing `moe_wq_` | none |
| X6, G2 (MoE verify windows) | the window's 3 extra positions in the KV cache and a few rows of scratch (KB to a few MB) | none |
| X7 (experts chosen by a use profile) | the same expert cache size | the same RAM tier size; the profile is a small table |
| A1, P2 (8-lane and Xe3 forms of X1) | as X1: less | none |
| A2 (resident decoded weights on 16 GB cards) | **more**: only opt-in or within the room left after the context and the expert cache; the log says how much | none |
| P1 (16-lane iGPU preset) | weights decoded just in time, as on the 140T: minimal by design | none |
| G1 (missed experts on the CPU) | **less**: the staging buffers for copied misses shrink with the share computed on the CPU | none extra: the experts are read in place from the RAM tier already there; per-thread scratch of a few MB |
| G3 (fewer, larger MoE launches) | none | none |
| G5 (IQ3 repacked in place) | none: the same bytes in another order; a per-tensor scratch at load only | none |
| G6 (the GEMV's bytes in flight per Xe-core) | none: registers and the existing local window only | none |
| Dense: resident int8 weights (`ARC_W8_PARTIAL_GB`) | **more**: stays opt-in or bounded by the free room | none |

## Where the ideas come from

urakozz/intel-arc-inference-server, one Arc Pro B70, his README and commit messages of 2026-11-11 to 11-16:

| | His (one B70) | Ours |
|---|---|---|
| Ornith 1.5 35B-A3B (int4, the Qwen3.5 35B-A3B shape), 4K prompt | **9,362 tok/s** (16K: 7,682) | Qwen3.6 35B-A3B UD-IQ4_XS on one B60: 3,536; on a B70 (issue #27, release 2026.11.16.12) 5,377 at 8K |
| The same, generation | 142.8 plain, **312 with MTP** (code) | B60: 82.4 plain, 111.9 with MTP |
| Qwen3.8 Flash Next on two B70s | 4K prompt 1,358, generation 49 plain / 70 with MTP (code) | the experts' gate / up are 45 % of a B70's Flash Next prompt (issue #27) |
| Qwen3.8 27B, one B70, 4K prompt | 2,083 (his int8 form now) | ~2,400 since release 2026.11.15.08 |

His Ornith prompt went 3,377 -> 9,362 tok/s in five days. From his commit messages, in order of size:

1. **The expert GEMMs read the int4 blocks directly** (`pf_moe_q4gemm`): one grouped GEMM on XMX over the tokens
   sorted by expert, no per-chunk pass that decodes the weights first. 3,377 -> 6,552 tok/s on its own (+94 %).
2. **The token sort over many work-groups:** 1.50 -> 0.05 ms per layer and chunk.
3. **Chunks of 4,096 rows**, and small kernels merged: the DeltaNet's conv + SiLU + l2norm in one launch; the
   residual add and the norm in one; the MoE combine and the next layer's norm in one. About +7 %.
4. **The router and the DeltaNet's a||b projection on the dense GEMM** instead of a GEMV: +6.5 %.
5. **int8 activations for the experts** (W4A8) on his int8 prompt pass.

Generation: MTP with a cost table measured on the card. On Ornith, drafting 3 tokens costs 0.57 of a plain step and
verifying 4 costs 1.52; MTP gives 2.2x. Flash Next: MTP on by default, a profile of which experts prose uses for
the experts kept in host memory (prose 15.5 -> 30 tok/s), and the two cards working on different prompt chunks at
once (1.33x at 4K).

**License.** Since 2026-11-17 00:00 CET his engine is AGPL-3.0 or commercial; earlier versions stay Apache-2.0.
Ideas from either are fine. Code may come only from commits before the cut-over (the last is `471c1efc`), credited as
`zero/kernels/h8.cl` credits his H8 code.

## Xe2: Arc B580, Pro B60, Pro B70 (and Lunar Lake's 16-lane XMX)

What our MoE prompt does today (`zero/engine_moe.h`): the router on the int8 GEMM; the sort as `moe_route` (per
token) + `moe_scan` (one work-group of n_expert) + `moe_scatter`; then, by chunk size, the per-tile kernels
(`moe_gateup_q` / `moe_down_q`, DP4a), `moe_rg` (DP4a on the raw expert rows, 320-1,279 tokens), or `moe_gemm`
(1,152+ tokens): `decode_w8` of every expert group to int8, then `gemm.cl -DMOE_TILES` on XMX with 16-token tiles.
A B60's 35B 16K prompt: the expert GEMMs 1.55 s of 5.08 s at ~21 TOPS, where our dense GEMMs reach ~50.

**Dense models on Xe2** (for completeness, from the comparison of 2026-11-15, docs/xe2-tuning.md sections 10-13):
the work-group change is done (`ARC_GEMM_XW_WGX=4`, +3.7 % on a B70); left are the GEMM's cooperative prefetch (each

10: the B70's FFN GEMVs at ~62 % of bandwidth, his int4 at 89-97 %).

## Alchemist: Arc A770, A750, A580 (Xe-HPG)

What these cards are to this engine: discrete, 16 GB GDDR6 at ~560 GB/s on an A770, XMX with **8-lane** DPAS (the
140T's kind, `cl_.sg8`), no 2D block loads (`cl_.block2d` is Xe2 / Xe3). Since 2026-11-16 they take the Arc 140T
preset by default (H8 on `gemm_xw8`, packed operands, weights decoded just in time). **No one has measured one with
this engine yet.**

## Xe3: Panther Lake (Arc B390 and the other iGPUs), and later discrete Xe3 cards

What these are to this engine: 16-lane DPAS and 2D block loads like Xe2 (the kernels build there: `ptl-h` shows real
`dpas.8x8` in all 19 GEMM builds, docs/xe2-tuning.md), no 8-lane sub-groups, memory shared with the CPU (LPDDR5x).

## Generation: what Strata and XeStrata do (added 2026-11-18)

Strata (Niko1221/Strata, MIT) runs Qwen3.8 Flash Next on a 12 GB GPU with 64 GB of RAM; XeStrata (MistVVK/XeStrata,
LGPL-3.0) is its SYCL / Level Zero port, developed on a Pro B70. XeStrata's B70 decodes Flash Next at 72-96 tok/s
(IQ3_XXS 71.9, IQ3_S 73.9 at 4K; its docs/DETAILS.md), with MTP on. Ours on a B70 (issue #27, joshdev-de, release
2026.11.16.12): Flash Next IQ3_S with 46 % of the experts in VRAM, a 41.5 ms median plain step (~24 tok/s); the 35B-A3B
a 10.0 ms step (100 tok/s), where urakozz's plain step is 7.0 ms.

**Their speed is not plain steps at full bandwidth.** Strata's paper (docs/paper/Strata-Paper.pdf, measured on CUDA):
a verify window of up to 4 tokens produces 3.2-3.6 of them; the GPU's part of a window is ~14-15 ms, mostly 3.5 GB of
dense weights, ~240 GB/s on a 672 GB/s card (worked out from the paper's numbers); the CPU computes the experts that are
not in VRAM in place, at the same time, and each half takes about half of the window. Nothing in it points at a fault of
Intel's GPUs: plain dense GEMVs reach 89-97 % of a B70's measured bandwidth in urakozz's engine. What costs on our side
is software and format choice (the codebook decode, small kernels and their launches; section 10 of docs/xe2-tuning.md).

| G6 | **The single-token GEMV with about twice the bytes in flight per Xe-core** (the user, 2026-11-19: "B65 user have higher bandwidth but generations staying the same"). A streaming read gets 30 GB/s a core on the B65 (`gpu_bench`). So generation follows the core count, not the bandwidth: the B60 and the B65 (both 20 cores) generate the same (27B 23.7 / 21.6-22.0 tok/s, 35B 82.4 / 82.0) although the B65 has 31 % more bandwidth. The Pro B60 (issue #4, 20 cores) agrees: FFN 25.0 ms = 295 GB/s = 69 % of 431, 14.8 GB/s a core, the B65's time with 39 % less bandwidth. **But the cap is not a fixed limit per core:** on the same 20-core cards the Q4_K output head reads 428 GB/s on the B60 (99 %, 21.4 a core) and 474 on the B65 (79 %, 23.7 a core), so a GEMV whose format is cheap to decode and whose rows are many pulls ~1.5x more a core. The FFN's cap looks specific to its IQ3 formats (the decode, or their access pattern), and two earlier pieces of evidence were weak (the B65's 4B figure was a whole token of small matrices, not one GEMV; the B70 is near its own bandwidth, so its per-core figure is no clock comparison). `ARC_IQ3S_TILE` lost on both cards. **The #47 runs decide which:** `ARC_GV_PROBE=1` (reads only) against `=2` (decode only) for gate / up / down. If the reads alone are much faster than the default, it is the decode, and F4's sign trick with the codebook in local memory come first; if about as slow, it is the access pattern, and this item's bytes in flight come first. Either way the target is at least the head's 21-24 GB/s a core. **Confirm first** (#47, teodortomas; the same on a B60 if an owner can): `ARC_GV_PROBE=1` (the access pattern, no decode) against the default with `--prof-gen`, and `ARC_GVROWS=1/2/4`, `ARC_GEMV_GRF=128/256`, `ARC_GEMV_DB=0/1` (`bench/decode_try.sh` has the rows). **Then build:** two windows or k-groups in flight, bigger contiguous block reads per sub-group, more independent rows per thread on 20-core cards, a deeper L1 prefetch, fewer barriers | `zero/kernels/decode.cl` (`gemv`, `gemv_v`), the launch shape in `zero/engine.h` and its per-GPU defaults in `zero/xe2/engine_xe2.h` (by Xe-core count) | target ~30 GB/s a core on the B60 / B65 (their full bandwidth), ~19 on the B70; the 27B on a B65 up to ~1.8x if the rest of the step allows (estimate); the 4B / 9B / 35B gain with it | bit for bit (the same sums in the same order); speed and `--prof-gen` per card | medium |

int4 copies or files are left out by the user's choice (more memory, and IQ3 -> int4 is not exact: an IQ3 block's two
sub-block scales and its codebook do not fit one int4 scale per 64 weights).

Order (the user, 2026-11-18: "both"): G3's measurement first (no code); then **G5, the IQ3 repack**, and **G2, more

## Flash Next: KL at or below 0.01 in the default mode, at full speed (the user, 2026-11-18; queued now)

**Target:** Flash Next's default (fast) mode at a next-token KL of **0.01 or less** against the f32 reference
(`tools/ref_forward`), measured as the memory rule "KL over long generations" asks (token by token over hundreds of
positions, the max reported, same top token >= 98 %), with no loss of prompt or generation speed beyond noise.
AGENTS.md lets the default mode reach ~0.02; this target is tighter.

**Why it is reachable:** the precise mode is already there: against f32, 0.00173 prompt / 0.00221 generation on 160
code tokens, and 0.0060 on the 3,584-token prose prompt, where the default mode measured 0.0105. So the parts that
precise mode keeps in float are where the default mode's extra error comes from. The default runs them on int8 because
the float kernels were slow: about half the prompt speed (docs/before-after.md 2026-11-14).

**What the other engines do** (research 2026-11-18: XeStrata, Strata and its forks, urakozz's engine up to
`471c1efc`, llama.cpp): none publishes a Flash Next KL against an f32 reference. None uses int8 or H8 activations for
the hyper-connection mixers: XeStrata keeps them, the router, alpha / beta, the indexer and PLE in bf16 (bf16
activations in the prompt, f32 in decode); urakozz keeps them in bf16 throughout. They use f16 hi + lo split products
on XMX where f32-level precision is needed (XeStrata's DeltaNet scan and prompt attention; Strata's chunked DeltaNet,
KL 0.0019). SwiGLU is in f32, rounded once, merged with the int8 quantization of the down projection's input (Strata,
XeStrata). Top-k selections take a fixed tie-break, lower id first (urakozz's QSA select).

## Multi-GPU: a layer split beside the tensor split (the user, 2026-11-19; queued)

Today `--gpus N` is tensor parallel only (docs/multi-gpu.md): every layer split over the GPUs, two sums a layer (128 a
token on the 27B). That wins where the sums are cheap: 4 B60s under Windows 27B 21.9 -> 53 tok/s (2.44x), 4K prompt
1.71x. It loses where they are not:
- 2 A770s under Windows without peer access (issue #35): 27B 12.6-12.8 -> 12.17 tok/s, 4K prompt 1,169 -> 1,126; 73.5
  ms of an 81 ms token in the sums, ~0.57 ms each (host round trips; `ARC_TP_EVSUM` took the host wait away but not
  the time: 12.33 -> 11.98);
- a B60 on a chipset x4 link (issue #19): a 4K prompt's ~5.4 GB of sums at 1.3-3.1 GB/s;
- cards too small for the model: a B580's 27B 7.1 tok/s with 0.49 GiB of weights over PCIe 3.0 (issue #37);
- mixed cards (a tensor split wants equal shards).

**A layer split** gives each GPU whole layers (GPU 0 the first part, GPU 1 the rest, sized by each card's memory and
speed) and passes the hidden state along once per stage boundary: one crossing a token (~20 KB on the 27B) instead
of 128 sums, ~84 MB per 4K prompt instead of ~5.4 GB. Generation runs the stages one after the other, so one request
gets about one card's speed; two requests in flight keep both busy. Prompts overlap: stage 0 runs chunk j + 1 while
stage 1 runs chunk j (urakozz's two B70s: 1.33x at 4K, 1.78-1.81x at 17-20K, on Flash Next). The logits are one GPU's
bit for bit (the same kernels in the same order; only a copy between stages), where the tensor split's sums change
the order. llama.cpp's default (`--split-mode layer`) is this, and the mode that works on Intel's SYCL backend.

| # | What to make or change | Where | Check | Size |
|---|---|---|---|---|
| L1 | **An engine over a range of layers**: stage 0 the embedding (and Flash Next's PLE), the last stage the norm, the head and the MTP block; each stage its layers' weights, KV cache, DeltaNet state and (MoE) expert cache only | `zero/mgpu/` (a `PpEngine` beside `TpEngine`), the layer range in `zero/engine.h` / `engine_load.h` | `ARC_TP_SIM=1`: two and three stages on one GPU, the logits bit for bit against one GPU (prompt + generation, the 4B, 27B, 35B) | large |
| L2 | **The hand-off**: the rows of the hidden state through pinned host memory, or GPU to GPU where `ARC_TP_P2P` finds peer access; one copy per chunk / token, an event between the stages, no host wait | `zero/mgpu/` | bit for bit (a copy) | medium |
| L3 | **Prompts pipelined**: pipeline chunks smaller than the prompt chunk (1,024 rows, say) so a 4K prompt has stages working at once; the next chunk's first stage while the last stage finishes this one | the prompt loop of the stage engine | bit for bit at the same chunk sizes; the 4K / 16K / 64K prompt against one card and against the tensor split | medium |

**What to expect** (estimates, to be measured): 2 A770s under Windows, the 27B: generation ~12.6 (one card's, against

hansong80's two A770s (#35), d-dorok's B580 (#37) with a second card if he has one, and manoreken2's B60s (#4) for the
