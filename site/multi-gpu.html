Several GPUs

inferzero can split one model over 2 to 4 Intel GPUs. Each card holds part of every layer, and the cards add their results together after each layer. This page says when that is worth it, how to start it, and how to make the cards talk to each other directly on Linux, which is where most of the speed comes from.

When it helps

Generation is limited by how fast weights are read from memory. Split over two cards, each reads half, so one conversation writes faster. The cost: after every layer the cards must add up their results, and how fast they can do that decides whether the split pays.

Tokens per second. tg = generation, how fast the answer is written; pp = prompt processing, how fast the prompt is read. Every number, with its release and who measured it: results.

Worth splitting

A model that does not fit on one card. And on Linux with direct copies (below), a model that does fit, for faster answers.

Usually not

On Windows, a model that fits one card: the drivers allow no direct copies between Arc cards, so the sums wait on host memory and two cards can be slower than one.

A slow slot

A card in a PCIe x4 slot (often a chipset slot) holds the pair back: one such setup read prompts at half of one card's speed. A split by layers, which needs far less traffic, is planned.

How to run it

  • Windows launcher: in the advanced options, set GPUs (one model split) to 2, 3 or 4 before starting the model.
  • Linux launcher: ./zero-launcher.sh --gpus 2.
  • Server or benchmark (from the package folder; bin\ on Windows): ./bin/serverz -m <model.gguf> --gpus 2, or ./bin/runz <model.gguf> --gpus 2 --bench-pp 4096 --n 128.

Qwen models (dense, the 35B-A3B, Flash Next) and DeepSeek-V4.1 split; a model that cannot be split loads on one GPU. Gemma 4 is not split yet, and drafting (MTP) is off on a split model. Several conversations at once (--slots) work split too.

Check your setup: do the cards copy directly?

On Linux, Intel's xe driver lets one GPU read another's memory only when the kernel was built with CONFIG_PCI_P2PDMA. Without it, everything still works, but every sum takes the detour through host memory. Two quick checks:

grep P2PDMA /boot/config-$(uname -r)          # want: CONFIG_PCI_P2PDMA=y
zcat /proc/config.gz | grep P2PDMA            # if the first file is missing

Then, from the inferzero folder, ./bin/mgpu_probe times every pair of GPUs. The peer column says whether the driver allows direct copies, and the rows compare direct copies with copies through host memory:

pair     peer   path                     20 KB (us)   40 MB (ms)       GB/s
0 -> 1   yes    direct, copy engine            13.4         8.68        4.8
0 -> 1   yes    via host, copy engine          18.4        14.46        2.9

Two Arc Pro B50s on PCIe 3.0 x8 (catduckgnaf, #59). With their distribution's stock kernel the direct rows failed and only the host path worked.

Turn on P2PDMA

If grep printed CONFIG_PCI_P2PDMA=y, there is nothing to do. If it printed # CONFIG_PCI_P2PDMA is not set or nothing:

  1. Easiest: use a kernel that has it. Your distribution's other kernels (a newer or "generic" one) may; the systems in the table above have it in their standard kernels.
  2. Or rebuild your kernel with it. In the kernel source, starting from your running kernel's configuration: 
    cp /boot/config-$(uname -r) .config
scripts/config --enable PCI_P2PDMA
make olddefconfig
grep P2PDMA .config        # must still say =y
    If olddefconfig turned it off again, a setting it needs is off: P2PDMA needs ZONE_DEVICE, which needs memory hot-plug and hot-remove (MEMORY_HOTPLUG, MEMORY_HOTREMOVE). Enable those the same way, then build and install the kernel as your distribution documents, and reboot into it.
  3. Unraid: its stock kernel lacks it. catduckgnaf rebuilt the same kernel (6.18.60) with CONFIG_PCI_P2PDMA=y, and direct copies worked (#59).

Slots and BIOS

Slots
Put the cards in slots wired to the CPU (x8 or x16), not a chipset x4 slot. With one card in a chipset x4 slot (2.4 GB/s), that link sets the pace for both.
Two CPUs
On a two-socket board, put both cards under the same CPU. Moving one B50 to the same socket as the other took the split prompt from ~710 to ~975 tok/s.
BIOS
Turn on Above 4G Decoding and Resizable BAR, as Arc cards need anyway.
IOMMU
If the driver reports peer access but the copies fail, the engine falls back to host memory and says so in its log; an IOMMU is usually in the way then. The working B50 machine ran its IOMMU in passthrough mode (iommu=pt on the kernel command line).

Confirm it works

At load, inferzero times every link and picks the faster path for the sums. Its log says which:

inferzero: links: GPU 0 -> host 12.1 GB/s, host -> GPU 0 11.8 GB/s, -> GPU 1 13.0 GB/s
inferzero: the GPUs' sums go straight from GPU to GPU (13.0 GB/s directly against 11.8 through host memory)

To compare both paths yourself, run the same benchmark with each forced:

ARC_TP_P2P=1 ./bin/runz <model.gguf> --gpus 2 --bench-pp 4096 --n 128   # direct
ARC_TP_P2P=0 ./bin/runz <model.gguf> --gpus 2 --bench-pp 4096 --n 128   # through host memory

On two Pro B60s with equal link speeds, direct was 13-17 % faster for prompts (1,630 against 1,442 tok/s) and the answers were identical bit for bit. With direct copies available the engine may still pick host memory where that measures faster: on Data Center GPU Max stacks it does for generation.

The design, every switch and its failsafes: docs/multi-gpu.md. Ran it on your machine? Post your results; two-card setups on new systems are especially welcome.
